# 기술 실험

각 실험은 하나의 가설을 가능한 한 작고 독립적으로 검증한다. 제품 코드나 공용 프레임워크를 먼저 만들지 않으며, 성공과 실패 모두 결과로 기록한다.

## 실험 기록 형식

```markdown
# 실험 제목

- 상태: 제안 | 진행 중 | 완료 | 중단
- 날짜: YYYY-MM-DD

## 목적

이 실험으로 알아내려는 것은 무엇인가?

## 가설

검증 가능하고 반증 가능한 예상은 무엇인가?

## 범위

포함하는 것과 의도적으로 제외하는 것은 무엇인가?

## 성공 조건

어떤 관측 결과를 성공으로 판단하는가?

## 테스트 방법

어떤 입력, 경계값과 반복 절차로 검증하는가?

## 결과

측정값, 실패 사례와 재현 방법은 무엇인가?

## 후속 결정

결과에 따라 채택, 수정, 폐기하거나 다음에 실험할 것은 무엇인가?
```

## 첫 실험 후보: 음수 좌표를 포함한 월드 좌표와 청크 좌표 변환

월드 좌표를 청크 인덱스와 청크 내부 좌표로 일관되게 분해하고 다시 조합할 수 있는지 검증한다. 특히 정수 나눗셈과 나머지 연산의 언어별 동작 때문에 발생할 수 있는 음수 좌표 경계 오류를 확인한다.

후보 성공 조건은 다음과 같다.

- 청크 내부 좌표가 항상 `0 <= local < chunkSize`를 만족한다.
- `-chunkSize`, `-1`, `0`, `chunkSize - 1`, `chunkSize`를 포함한 경계값이 예상한 청크에 속한다.
- 좌표를 분해한 뒤 다시 조합하면 원래 월드 좌표와 일치한다.

구현 언어, 청크 크기와 테스트 프레임워크는 아직 선택하지 않는다. 이 항목은 실험 후보 기록이며 코드 구현이 아니다.

## 후속 실험 후보: 이동과 2인 공중 급유

아래 순서는 확정된 개발 일정이 아니라 이동과 협력 경험을 작은 단계로 분리해 검증하기 위한 후보 순서다. 각 단계는 앞선 결과가 유효할 때만 다음 실험으로 승격한다.

1. 걷기
2. 달리기
3. 점프
4. 8방향 공중 대쉬
5. 연속 공중 대쉬
6. 체공
7. 급강하
8. 공중 자원 게이지
9. 2인 멀티플레이 위치 동기화
10. `F` 기반 원형 상호작용
11. 상대 플레이어 공중 자원 충전
12. 먼 거리에서 추락 중인 플레이어 구조
13. 필요성이 확인된 이후 벽타기, 매달리기와 지상 슬라이드

첫 2인 멀티플레이 실험에서는 완성된 캐릭터 그래픽 대신 임시 사각형을 사용할 수 있다. 다음 경험만 우선 검증한다.

- 두 플레이어가 서로 보이고 독립적으로 이동한다.
- 한 플레이어의 공중 이동이 자원을 소모한다.
- 다른 플레이어가 `F` 상호작용으로 그 자원을 회복시킨다.
- 먼 거리에서 추락 중인 플레이어를 구조해 공중 이동으로 복귀시킬 수 있다.

### 2026-09-09 진행 상황

위 후보 순서 중 1~5를 임시 사각형으로 구현하고 Windows에서 빌드·실행한 뒤 사람이 직접 조작해 확인했다. 순서상 13번이던 벽 슬라이드는 벽 점프를 검증하기 위해 먼저 구현했다.

| 단계 | 상태 | 비고 |
| --- | --- | --- |
| 1. 걷기 | 완료 | delta time 기반 |
| 2. 달리기 | 완료 | 같은 방향 더블탭 후 유지, 약 0.3초 가속 |
| 3. 점프 | 완료 | 중력, 플랫폼 착지, grounded 판정 포함 |
| 4. 8방향 공중 대쉬 | 완료 | 대각선은 두 번째 탭 순간의 두 축을 조합 |
| 5. 연속 공중 대쉬 | 완료 | 횟수 제한 없음, 대쉬 중 재발동만 차단 |
| 6. 체공 | 완료 | 위 홀드 시 낙하 속도 제한, 상승은 만들지 않음 |
| 7. 급강하 | 완료 | 아래 홀드 시 가속, 벽에서는 벽 슬라이드를 우선 |
| 8. 공중 자원 게이지 | 미착수 | |
| 9 이후 | 미착수 | |
| 13. 벽 슬라이드 | 순서를 앞당겨 완료 | 벽 접촉 시 점프 재사용을 함께 검증 |

함께 만든 것은 다음과 같다.

- 화면보다 넓은 practice room과 `sf::View` 기반 follow camera. 수직은 dead-zone과 지수 감쇠 smoothing을 쓰며, 급강하 중에는 추적 속도를 높인다.
- 명시적인 이동 상태 모델. 현재 상태를 창 제목에 표시해 코드 밖에서 확인할 수 있다.
- `tests/`의 회귀 테스트. 외부 테스트 라이브러리 없이 CTest로 실행하며, 지형 관통, 대쉬 속도에서의 터널링, 키 반복으로 인한 오발동, delta time 독립성, 벽 없이 공중에서 다시 점프되지 않는지, 등반 경로의 도달 가능성을 확인한다.

아직 답하지 못한 것은 다음과 같다.

- 현재 이동 수치가 장시간 플레이에서도 적절한지. 지금 값은 모두 후보값이다.
- 체공과 급강하까지 더한 조작 체계가 장시간 플레이에서도 복잡하게 느껴지지 않는지.
- 벽에 붙은 상태에서 급강하를 막아 둔 현재 우선순위가 적절한지.
- 벽을 타고 연속으로 올라가는 이동이 지형 설계에 어떤 영향을 주는지.

이 단계는 아직 정식 실험 기록이 아니라 이동 규칙을 만들기 위한 프로토타입이다. 위 항목 중 독립적으로 반증할 수 있는 것이 생기면 문서 상단의 실험 기록 형식으로 분리한다.

## 후속 실험 후보: 공통 스프라이트 규격

이 실험은 이동 규칙을 임시 사각형으로 먼저 검증한 뒤, 테스트 아바타 한 종으로 공통 스프라이트 규격이 성립하는지 확인한다. 특정 캔버스 크기, 프레임 수 또는 atlas 배치를 확정하는 실험이 아니다.

1. 임시 사각형으로 이동 시스템 검증 (2026-09-09 완료, 위 진행 상황 참고)
2. 고정 크기 프레임을 가진 테스트 아바타 한 종 적용 (2026-09-10 proto_one 적용 완료)
3. Idle, Walk와 Run 애니메이션 전환 (2026-09-10 완료. Run 은 코드의 Sprinting 상태에 연결)
4. Jump와 Air Dash 적용
5. 공통 pivot의 시각적 흔들림 검증
6. collider와 sprite 분리 검증
7. 2프레임 Music 애니메이션 적용
8. 다른 2~4종 아바타를 같은 규격으로 교체할 수 있는지 검증

성공 조건 후보는 모든 프레임의 캔버스와 pivot이 일관되고, `visualOffset`이 물리 상태를 바꾸지 않으며, 아바타 교체 시 animation state나 atlas 해석 코드를 변경하지 않는 것이다. 여기에 더해 같은 상태에서 아바타 간 프레임 수가 동일해야 한다. 이는 실험으로 판단할 후보가 아니라 지켜야 할 규칙이며 [`docs/animation-policy.md`](../docs/animation-policy.md)의 공통 애니메이션 프레임 계약을 따른다. 상태별 채택값은 같은 문서의 Current Animation Contract에서 확인한다. asset을 만들기 전에 그 표부터 본다.
