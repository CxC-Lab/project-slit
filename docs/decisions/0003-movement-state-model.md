# 0003: 이동 상태를 명시적 모델로 두되 프레임워크로 키우지 않는다

- 상태: 채택
- 날짜: 2026-09-09

## 결정 내용

플레이어의 이동 상태를 `MovementState` 열거형으로 명시하고, 상태 결정을 `Player` 안의 한 함수에서만 수행한다.

상태는 `Idle`, `Walking`, `Sprinting`, `Jumping`, `Falling`, `AirDashing`, `WallSliding`, `SlowFalling`, `FastFalling`이다. 상태 이름을 문자열로 바꾸는 함수를 함께 두고, 현재는 창 제목에 표시해 사람이 코드 밖에서 확인한다.

상태는 물리 사실을 대체하지 않는다. 접지 여부, 벽 접촉, 속도, 위치는 그대로 실제 데이터로 남고, 상태는 그 값과 입력으로 결정된다. 흐름은 물리 사실 → 상태 결정 → 상태별 동작이다.

## 배경

이동 기능이 걷기와 점프에서 시작해 달리기, 8방향 공중 대쉬, 벽 슬라이드, 벽 재점프, 체공, 급강하까지 늘었다. 이 시점에서 "지금 플레이어가 무엇을 하고 있는가"를 조건문 조합으로만 판단하게 되었고, 같은 판단이 여러 곳에 흩어지기 시작했다.

앞으로 애니메이션, 파티클, 사운드, 카메라 반응, 멀티플레이 표현이 모두 이 판단을 참조해야 한다. 각자가 조건문을 다시 조합하면 서로 다른 답을 내게 된다.

## 검토한 대안

- 조건문을 그대로 두고 필요한 곳에서 매번 판단한다: 추가 구조가 없다. 다만 같은 판단이 중복되고, 조건이 하나 바뀔 때 모든 사용처를 찾아야 한다.
- 범용 상태 머신이나 Ability System을 도입한다: 전이 규칙을 선언적으로 관리할 수 있다. 다만 현재 상태는 아홉 개이고 전이 규칙도 단순하다. 지금 도입하면 검증할 대상이 없는 계층만 늘어난다.
- 열거형과 단일 결정 함수를 둔다: 사용처는 상태 하나만 읽으면 되고, 규칙이 바뀌면 고칠 곳이 한 군데다.

## 선택 이유

세 번째 방식으로 체공과 급강하를 추가하는 동안 입력 계층과 지형, 빌드 설정을 전혀 수정하지 않아도 되었고, 새 파일도 만들지 않았다. 상태를 창 제목에 표시하자 조작하면서 전이가 맞는지 바로 확인할 수 있었고, 이는 폰트 asset이나 디버그 UI 없이 가능했다.

상태와 물리 사실을 분리해 둔 덕분에 낙하 제한처럼 상태에 따라 달라지는 규칙만 상태를 참조하고, 충돌 해소는 계속 실제 속도와 위치로만 처리한다. 두 표현이 어긋나 모순될 여지를 줄이기 위한 구분이다.

이 결정은 [`0002-minimal-source-structure.md`](0002-minimal-source-structure.md)의 "필요해질 때까지 계층을 만들지 않는다"는 기준을 이동 상태에 적용한 것이다.

## 되돌릴 조건

다음 중 하나가 실제로 발생하면 재검토한다.

- 상태 수가 크게 늘어 단일 결정 함수가 한눈에 읽히지 않게 된 경우
- 상태마다 진입과 종료 시점에 실행할 동작이 생겨 전이 자체를 자료로 다뤄야 하는 경우
- 상태가 서로 겹쳐 하나의 열거형으로 표현할 수 없게 된 경우. 예를 들어 이동 상태와 별개로 유지되는 상태를 동시에 가져야 하는 경우
- 플레이어 외의 대상도 같은 상태 모델을 필요로 하게 된 경우

위 상황이 오기 전에 미리 상태 머신 프레임워크를 도입하지 않는다.
