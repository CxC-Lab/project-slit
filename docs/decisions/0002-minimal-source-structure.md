# 0002: 필요해질 때까지 엔진 계층을 만들지 않고 최소 구조를 유지한다

- 상태: 채택
- 날짜: 2026-09-09

## 결정 내용

프로토타입 코드는 `src/` 아래에 기능 단위 파일로만 나눈다. ECS, 범용 Entity/Component 프레임워크, Scene 시스템, 이벤트 버스, 범용 physics engine, 범용 camera framework 같은 계층을 미리 만들지 않는다.

파일은 그 파일 없이 다른 파일이 비대해질 때만 나눈다. 코드 몇 줄로 끝나는 기능에 클래스나 추상화를 만들지 않는다.

## 배경

이 저장소의 목적은 게임 엔진을 만드는 것이 아니라 가설을 검증하는 것이다. 검증되지 않은 요구에 맞춰 구조를 먼저 세우면, 나중에 가설이 바뀔 때 구조가 판단을 제약한다.

동시에 한 파일에 모든 것을 계속 쌓으면 다음 기능을 추가할 때마다 수정 범위가 커지고 회귀를 알아채기 어려워진다. 두 실패 사이에서 기준이 필요했다.

## 검토한 대안

- 처음부터 ECS나 컴포넌트 구조를 세운다: 엔티티가 늘어날 때 유리하다. 다만 현재 엔티티는 플레이어 하나이고, 지형은 사각형 목록이다. 지금 도입하면 검증 대상이 없는 복잡도만 남는다.
- 모든 코드를 `main.cpp`에 유지한다: 가장 단순하다. 다만 이동 규칙이 늘어나면서 실제로 한 파일이 커지는 것을 확인했다.
- 기능이 실제로 커질 때만 파일을 나눈다: 판단 기준이 사람에 따라 흔들릴 수 있다. 대신 "이 파일이 없으면 다른 파일이 비대해지는가"를 기준으로 삼으면 매번 되물을 수 있다.

## 선택 이유

세 번째 방식이 실제로 동작하는지 두 차례 확인했다.

`main.cpp`가 109줄이 되었을 때 이동과 입력을 `Player`와 `Input`으로 분리했고, `main.cpp`는 64줄로 줄었다. 반대로 follow camera를 처음 넣었을 때는 코드가 몇 줄이라 `Camera` 파일을 만들지 않았고, 이후 수직 dead-zone과 smoothing이 붙어 계산이 독립적으로 검증할 만한 크기가 되었을 때 `Camera` 파일로 분리했다.

같은 기준을 테스트에도 적용해, 외부 테스트 라이브러리를 추가하지 않고 CTest와 표준 라이브러리만으로 회귀 테스트를 작성했다.

이 방식으로 다섯 번의 기능 추가를 거치는 동안 회귀가 발생하지 않았고, 각 단계의 변경 범위는 검토 가능한 크기로 유지되었다.

## 되돌릴 조건

다음 중 하나가 실제로 발생하면 구조 방침을 재검토한다.

- 플레이어 외에 상태와 갱신 주기를 가진 엔티티가 여러 종류 생기고, 파일 단위 분리로는 중복을 줄일 수 없는 경우
- 서로 다른 화면이나 모드 사이의 전환이 필요해져 수동 분기가 관리 범위를 넘는 경우
- 헤드리스 서버와 클라이언트가 같은 시뮬레이션 코드를 공유해야 하고, 현재 구조로는 렌더링과 시뮬레이션을 분리할 수 없는 경우

위 상황이 오기 전에 미리 도입하지 않는다. 도입할 때는 그 시점의 실제 문제를 근거로 후속 ADR을 남긴다.
