# 0008: 배경을 지역과 분리된 데이터 파일의 시차 레이어로 둔다

- 상태: 채택
- 날짜: 2026-09-12

## 결정 내용

배경은 지역 파일과 같은 이름의 별도 JSON 파일에 둔다. `assets/regions/avatar_lake.json` 의 배경은 `assets/backgrounds/avatar_lake.json` 이다. 같은 이름의 배경 파일이 없으면 그 지역은 단색 배경을 쓴다. 실패가 아니다.

배경 파일은 레이어 목록 하나만 담는다. 레이어 하나는 이미지 경로, 시차 계수, 기준 위치, 가로 반복 여부를 가진다.

```json
{"image":"avatar_lake/sky.png", "parallax":[0.02,0.02], "anchor":[0,-390], "repeatX":true}
```

배치 규칙은 하나다.

```
position = anchor + cameraCenter * (1 - parallax)
```

`parallax` 가 1 이면 월드에 고정되고, 0 이면 화면에 고정된다.

배경을 그리는 코드는 하늘, 호수, 절벽 같은 역할 이름을 알지 못한다. 레이어 개수도 고정하지 않는다. Avatar Lake 가 몇 장을 쓰는지는 데이터 파일만 안다.

### 확대 축소를 하지 않는다

배경 정점의 텍스처 좌표는 `월드 좌표 - 레이어 원점` 이다. 텍셀 하나가 월드 단위 하나에 대응하고, 이 비율은 가로와 세로가 항상 같다. 배경 경로에는 크기를 조절하는 코드가 없다.

따라서 그림이 늘어나는 일은 렌더링에서 발생할 수 없다. 늘어난 그림이 보인다면 원본 이미지가 이미 늘어나 있는 것이다.

### 세로 커버리지는 부등식으로 도출한다

레이어가 카메라 전체 범위에서 화면을 덮으려면 다음을 만족해야 한다. `py` 는 세로 시차, `H` 는 이미지 높이, `Vh` 는 보이는 세로 범위다.

```
H >= Vh + (cMax - cMin) * py
top(cMin) <= cMin - Vh/2        (뒤가 비치면 안 되는 불투명 레이어에만 해당)
top(cMax) + H >= cMax + Vh/2
```

창 모드 4:3 과 전체 화면 16:9 를 모두 만족해야 한다. 4:3 쪽이 세로로 더 넓게 보이므로 대개 이쪽이 결정한다.

높이와 `anchor` 는 눈으로 맞추지 않고 이 부등식에서 도출한다. 검사는 `tests/BackgroundTests.cpp` 에 있다.

### 부분 투명도를 쓰지 않는다

배경 이미지의 알파는 0 또는 255 만 허용한다. 중간값을 쓰지 않는다.

## 배경

다음 단계가 첫 월드인 Avatar Lake 의 분위기를 만드는 일이다. 분위기는 계산해서 나오지 않고 실제로 움직여 보며 찾아야 한다. 지형처럼 배경도 다시 빌드하지 않고 고칠 수 있어야 했다.

[`0007-regions-as-data.md`](0007-regions-as-data.md) 의 열린 질문 중 "배경과 시차 레이어를 같은 파일에 둘 것인가, 나눌 것인가" 가 여기에 해당한다.

## 검토한 대안

- 지역 파일 안에 배경 레이어를 함께 둔다: 파일이 하나로 줄어든다. 다만 지형을 고치는 일과 배경을 고치는 일은 주기와 담당이 다르다. 한 파일에 두면 배경을 다듬는 동안 지형 값이 같은 diff 에 섞인다.
- 배경을 코드에 둔다: 지형에서 이미 같은 이유로 물러난 선택이다.
- 별도 파일로 나누되 지역 파일이 배경 파일 이름을 명시한다: 유연하지만 지금은 지역 하나에 배경 하나뿐이라 이름을 한 번 더 적는 일만 늘어난다.

## 선택 이유

두 번째와 세 번째 사이에서 이름 규칙을 택했다. 지역과 배경을 나누되 연결은 파일 이름으로 한다. 연결 정보를 따로 적지 않으므로 어긋날 곳이 없고, 배경이 없는 지역은 파일을 만들지 않는 것으로 표현된다. `PracticeRoom` 이 실제로 그 상태다.

역할 이름을 코드에 넣지 않은 이유는 단순하다. Avatar Lake 다음 월드가 호수와 절벽을 쓸지 알 수 없다. 지금 이름을 넣으면 두 번째 월드에서 바로 걷어내야 한다.

부분 투명도를 뺀 이유도 같은 성격이다. 반투명은 레이어 순서와 색 합성을 함께 관리해야 하고, 아직 후처리도 날씨도 없는 상태에서 그 비용을 먼저 낼 이유가 없다. 필요해지면 그때 연다.

## 검증에서 배운 것

첫 시도는 기술 검증만 통과하고 시각적으로는 판정할 수 없었다. 원인은 두 가지였고 둘 다 렌더링이 아니라 에셋 쪽이었다.

콘셉트 아트를 가로 0.5배, 세로 2.14배로 표본화해 하늘을 만들었다. 이방성이 약 4.3배였고 구름이 세로로 늘어나 보였다. 나머지 레이어는 콘셉트 아트와 무관한 절차적 능선이라 서로 다른 그림이 겹친 것처럼 읽혔다.

그래서 에셋 생성기에 두 가지 규칙을 두었다.

- 소스 이미지를 표본화해 크기를 바꾸지 않는다. 참조가 필요하면 1:1 복사나 정수 배율만 쓴다.
- 가로와 서로 다른 세로 배율을 쓰는 코드는 두지 않는다.

현재 생성기(`tools/generate_background.cpp`)는 소스 이미지를 아예 읽지 않고 목적지 픽셀을 직접 그린다. 자동 실행하지 않으며, 명시적으로 실행할 때만 PNG 를 덮어쓴다.

또 하나 배운 것은 레이어가 각각 그럴듯한지가 아니라 시작 지점에서 한 장면으로 읽히는지가 판정 기준이라는 점이다. 호수 수면선을 지면 바로 위에 오도록 맞추고 나서야 풍경으로 보였다.

## 되돌릴 조건

- 한 지역에 여러 배경이 필요해진 경우. 시간대나 날씨로 배경이 바뀌면 이름 규칙만으로는 부족하다.
- 반투명이 실제로 필요해진 경우. 안개나 빛 산란을 레이어로 표현하기로 하면 알파 규칙부터 다시 본다.
- 배경이 카메라 외에 다른 것에 반응해야 하는 경우. 시차 계수만으로는 표현할 수 없다.
- 레이어 수가 많아져 한 장면당 그리기 호출이 성능 목표를 넘는 경우.

## 열린 질문

- 시차 계수와 레이어 구성은 아직 확정이 아니다. 검증용 임시 이미지에서 나온 값을 실제 아트에 그대로 쓰고 있으며, 오래 이동해 보고 다시 판단한다.
- 가로로 반복하는 방식이 열두 화면 폭에서 반복감을 만드는지 아직 판정하지 않았다.
- 전경 레이어를 다시 넣을지, 넣는다면 충돌 지형과 어떻게 구분할지 정하지 않았다.
