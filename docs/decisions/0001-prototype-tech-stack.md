# 0001: 초기 프로토타입에 C++20 + SFML 3 + CMake를 사용한다

- 상태: 채택
- 날짜: 2026-09-09

## 결정 내용

Project Slit의 초기 프로토타입을 C++20, SFML 3, CMake로 만들고 Windows x64에서 Visual Studio 2022로 빌드한다. DirectX 11/12와 HLSL 직접 작성은 이 단계에서 사용하지 않고 deferred 상태로 둔다.

이 결정은 초기 프로토타입 범위에 한정되며 Project Slit 전체 수명의 최종 기술 결정이 아니다.

## 배경

초기 단계에서 검증해야 하는 것은 렌더링 기술이 아니라 이동, 점프, 공중 이동, 충돌, 입력 같은 게임플레이 규칙이다. 이 규칙들은 실제로 조작해 보기 전에는 판단할 수 없으므로, 화면에 무언가를 띄우고 조작할 수 있는 상태에 빠르게 도달하는 것이 중요했다.

Win32와 DirectX를 직접 초기화하면 창 생성, 스왑체인, 셰이더 파이프라인 같은 렌더링 보일러플레이트에 시간을 쓰게 되고, 그 시간은 이동 규칙 검증에 기여하지 않는다.

## 검토한 대안

- Win32 + DirectX 11 직접 구현: 저수준 통제와 학습 가치가 크다. 다만 첫 조작 가능한 화면까지의 거리가 멀고, 지금 검증하려는 것과 관련이 적다.
- 범용 게임 엔진 사용: 가장 빠르게 시작할 수 있다. 다만 이 프로젝트는 결정론적 월드 생성과 권위형 서버 같은 가설을 직접 다루려는 목적이 있어, 엔진의 구조에 먼저 종속되는 것이 이르다고 판단했다.
- SFML 3: 창, 입력, 2D 렌더링, 뷰를 얇게 감싸는 수준이라 게임플레이 코드에 집중할 수 있다. 엔진처럼 프로젝트 구조를 강제하지 않는다.

## 선택 이유

2026-09-09에 이 스택으로 실행 가능한 이동 프로토타입을 만들어 좌우 이동, 점프, 중력, 플랫폼과 벽 충돌, 벽 슬라이드, 연속 벽 점프, 8방향 공중 대쉬, 지상 달리기, follow camera까지 구현하고 사람이 직접 조작해 확인했다.

이 과정에서 SFML의 렌더링 추상화가 제약이 된 지점은 없었다. 필요한 것은 사각형 렌더링과 `sf::View` 이동뿐이었고, 특수한 셰이더나 성능 문제도 발생하지 않았다. 즉 DirectX를 직접 다뤄야 할 실제 이유가 아직 관측되지 않았다.

CMake는 Visual Studio 생성기로 `.sln`을 만들 수 있으면서도 빌드 정의의 기준을 IDE 밖에 둘 수 있어 선택했다. 의존성은 FetchContent로 SFML 하나만 가져오며, 오디오와 네트워크 모듈은 끈 상태로 빌드한다.

## 되돌릴 조건

다음 중 하나가 실제로 관측되면 이 결정을 재검토한다. 예상이나 우려만으로는 바꾸지 않는다.

- SFML의 렌더링 추상화 때문에 원하는 표현을 만들 수 없는 사례가 나온 경우
- 특수 셰이더나 렌더링 기법이 필요해졌고 SFML로는 접근할 수 없는 경우
- 프로파일링으로 SFML 계층이 병목임이 확인되고 우회할 방법이 없는 경우
- 저수준 그래픽스 API 연구 자체가 프로젝트의 목표가 된 경우

재검토하더라도 기록을 삭제하지 않고 후속 ADR로 대체 관계를 남긴다.
