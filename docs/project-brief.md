# Project Slit 개요

이 문서는 Project Slit의 현재 방향과 가설을 공유하기 위한 살아 있는 문서다. 완성된 요구사항 명세가 아니며, 실험 결과와 프로젝트의 변화에 따라 내용을 수정하거나 폐기할 수 있다.

최초 게임플레이 콘셉트 아트에서 읽을 수 있는 방향과 검증 질문은 [`visual-direction.md`](visual-direction.md)에서 관리한다.

Project Slit은 이중슬릿 실험에서 영감을 받은 내부 코드네임이다. 관측되지 않은 세계는 가능성으로 존재하고 플레이어가 접근할 때 공간과 사건으로 구체화된다는 은유를 담고 있다. 이름은 최종 출시명이 아니다.

## 확정된 방향

- CxC Lab에서 진행하는 1인 연구개발 프로젝트로, 새 환경과 새 저장소에서 시작한다.
- 초기 목표는 완성된 게임이나 범용 엔진을 만드는 것이 아니라 독립적인 기술 실험과 Unit Test를 통해 아이디어를 검증하는 것이다.
- 검증된 결과만 실제 게임의 기반으로 발전시키며, 실패한 가설은 수정하거나 폐기한다.
- 게임으로 발전할 경우 이동, 발견, 분위기와 다른 플레이어와의 가벼운 조우를 핵심 경험으로 지향한다.
- 세계 전체를 미리 구현하기보다 작은 관측과 실험을 통해 설계와 기술을 선택한다.
- 변경 가능한 기획과 기술 가설은 문서로 관리하고, 중요한 선택은 ADR로 남긴다.
- 외부 작품은 출처와 참고 이유를 기록한 분석 자료로만 사용하며 고유한 캐릭터, 구도나 실루엣을 직접 복제하지 않는다.

2026-09-11에 경험의 성격을 좀 더 분명히 했다. 이 게임은 정확한 점프로 장애물을 넘는 재미를 목표로 하지 않는다. 넓은 공간을 자유롭게 떠다니며 분위기와 장소를 발견하는 쪽이다. 분위기와 음악, 시각적 매력이 레벨의 정교함보다 앞선다.

- 8방향 공중 대쉬와 벽 이동으로 웬만한 곳에 갈 수 있는 것은 문제가 아니라 의도한 즐거움이다. 이동을 제한해 길을 만드는 설계를 하지 않는다.
- 발판은 정답 경로를 만드는 장치가 아니라 쉼터, 관측 지점, 방향 표식에 가깝다.
- 2인 플레이는 흥을 돋우는 요소이며 정밀하게 제어할 대상이 아니다. 둘이 없으면 막히는 구조를 만들지 않는다. 둘이면 세계가 조금 더 풍부하게 반응하는 정도로 둔다.
- 따라서 레벨의 난이도 곡선이나 자원 관리보다, 텅 빈 공간에서 헤엄치듯 떠다니는 감각이 먼저다.

## 기술적 가설

아래 항목은 모두 후보이며 기술 스택이나 제품 요구사항으로 확정되지 않았다.

- Windows PC에서 동작하는 C++ 기반 경량 2D 런타임
- 물리 해상도와 논리 월드 뷰를 분리해 모니터 해상도가 달라도 구도와 캐릭터 크기 관계를 유지하는 표시 방식. 기준 구도와 화면비 처리 방식은 교체 가능하게 한 곳에서 관리한다. 배경과 되돌릴 조건은 [`decisions/0005-display-and-view-policy.md`](decisions/0005-display-and-view-policy.md)에 기록했다.
- DirectX 11 또는 DirectX 12 기반 렌더링과, DirectX를 선택할 경우의 HLSL 셰이더 작성. 초기 프로토타입은 SFML 3을 사용하며, 이 항목은 현재 필수 스택이 아니라 필요가 확인될 때 재검토할 deferred 후보다. 자세한 관계는 아래 "초기 프로토타입 기술 스택" 참고.
- 고정 60Hz 시뮬레이션과 Sweep 또는 CCD 방식의 고속 충돌 처리
- 같은 시드와 좌표가 같은 결과를 만드는 결정론적 월드 생성과 세그먼트 또는 청크 단위 로드·언로드
- 하나의 통짜 초대형 맵이 아니라 여러 대형 지역으로 나뉘는 월드. 지역 내부는 넓고 연속적으로 두고 지역 사이는 완충 구간으로 잇는 방향이며, 위의 청크 단위 로드는 지역 내부의 로드 단위로 둔다. 배경과 되돌릴 조건은 [`decisions/0004-region-based-world-structure.md`](decisions/0004-region-based-world-structure.md)에 기록했다.
- 생성 규칙, 시드와 최소한의 플레이어 흔적만 영속화하는 월드
- 플레이어 주변 구간만 동기화하는 Interest Management
- 렌더링 없이 클라이언트와 독립적으로 실행되며 게임 상태를 판정하는 권위형 Headless Server. 이는 Unreal Engine을 사용한다는 의미가 아니라 Unreal Dedicated Server와 역할이 유사한 실행 모델을 뜻한다.
- 클라이언트와 서버를 별도 실행 대상으로 구성하되, 현재 저장소 안에서 함께 관리하는 모노레포
- 2D 횡스크롤 또는 사이드뷰 및 필요할 때만 사용하는 논리적 보조 레이어
- 걷기, 점프, 대시, 벽 이동, 슬라이딩 등 속도감 있는 이동 방식
- 플레이어가 최대 3개의 표식이나 깃발을 남기는 비동기적 상호작용
- 거리에 따라 다른 플레이어의 채팅 내용이 점진적으로 표시되는 근접 채팅. 구체적인 거리값과 표시 알고리즘은 아직 정하지 않는다.
- MIDI를 제어 가능한 이벤트 데이터로 사용하고 SoundFont를 음색 후보로 삼는 동적 음악 시스템
- 지역, 날씨, 시간대, 이동과 조우에 따라 음악 레이어를 변화시키는 독립 모듈
- 황야, 수직 기계 도시, 폐허가 된 침수 도시, 주홍빛 단풍 산악 지대, 하늘 성당, 지하 수로, 네온사인 도시, 꽃과 물레방아가 있는 스팀펑크풍 시골 등 서로 다른 분위기의 지역 후보
- 다층 플랫폼과 거대한 구조물, 비·무지개·안개 등의 날씨, 조명과 후처리로 깊이감을 만드는 콘셉트 아트 방향
- 픽셀 캐릭터와 스프라이트 애니메이션을 포함한 아트 스타일 후보
- 다수의 사전 제작 2D 로봇형 픽셀 아바타가 하나의 스프라이트·애니메이션 규격을 공유하는 방식. 초기 상한 후보는 64종이나 수량은 미확정이며, 한 종으로 규격을 검증한 뒤 확대한다. 공유 규격 중 "모든 아바타는 같은 상태에서 같은 프레임 수를 사용한다"는 부분은 2026-09-10에 확정했다. 상태별 프레임 수의 구체적인 값은 대부분 아직 후보이며, 채택이 끝난 값은 [`animation-policy.md`](animation-policy.md)의 Current Animation Contract 한 곳에서만 관리한다. 2026-09-11 기준으로 열두 동작의 값이 모두 정해졌다. Idle, Walking, Sprinting, WallSliding, Landing 이 4프레임, Turn 과 Jumping, Falling, AirDashing 이 3프레임, SlowFalling 과 FastFalling 이 2프레임이다. Turn 과 Landing 은 이동 상태가 아니다. 각각 방향이 바뀔 때와 착지 충격이 있을 때 잠깐 재생된다.
- 런타임 생성형 AI보다 사전 제작 아바타 선택을 우선 검토하고, AI는 개발 중 시안과 에셋 제작을 보조하는 용도로 제한하는 방향
- 제작 보조 또는 별도 실험으로서의 AI, 에이전트, MCP와 A2A 연계

### 초기 프로토타입 기술 스택

현재 초기 프로토타입을 진행하기 위한 기준이며, Project Slit 전체 수명 동안 변경 불가능한 최종 기술 결정으로 기록하지 않는다. "작은 실험으로 검증하고 살아남은 결과만 확정한다"는 원칙에 따라 SFML을 포함해 아래 항목 모두 향후 검증 결과에 따라 교체될 수 있다.

- Platform: Windows x64
- Language: C++20
- 2D Framework: SFML 3
- Build: CMake
- Development Environment: Visual Studio 2022. CMake의 Visual Studio generator를 사용할 수 있으며, 이 경우 `.sln` / `.vcxproj`가 생성될 수 있다. 다만 Visual Studio solution 자체를 프로젝트의 원본 빌드 정의로 취급하지 않고 CMake를 기준으로 한다.
- Version Control: Git, GitHub

#### SFML 선택 목적

SFML을 선택한 현재 목적은 범용 게임 엔진을 구축하기 위한 것이 아니다. Project Slit 초기 단계에서는 플레이어 이동, 점프, 공중 이동, 2D sprite, animation, input, collision과 이후 multiplayer prototype을 빠르게 검증해야 한다. Win32 + DirectX를 직접 초기화하는 것보다 SFML을 이용해 불필요한 렌더링 보일러플레이트를 줄이고 게임플레이 실험에 집중하는 방향을 현재 프로토타입 기준으로 삼는다.

#### DirectX / HLSL의 현재 위치

DirectX 11 직접 렌더링, DirectX 12, HLSL 직접 작성은 현재 프로토타입의 필수 기술 스택이 아니다. 다만 Project Slit에서 영구적으로 배제된 기술도 아니며, 다음과 같은 이유가 실제로 발생할 경우 별도 기술 실험 대상으로 다시 검토할 수 있다.

- SFML의 렌더링 추상화가 요구사항을 제한하는 경우
- 특수 shader 또는 rendering technique가 필요한 경우
- 성능 문제를 직접 해결할 필요가 있는 경우
- 저수준 graphics API 연구의 가치가 확인되는 경우

현재 관계는 다음과 같다.

- Current prototype: C++20 + SFML 3 + CMake + Visual Studio 2022 + Windows x64
- Deferred / future investigation: DirectX 11 / DirectX 12 / HLSL

#### 2026-09-09 구현 현황

위 스택으로 실행 가능한 이동 프로토타입을 만들고 Windows에서 빌드와 실행을 확인했다. SFML 3은 창 생성, 키 입력, 사각형 렌더링과 `sf::View` 기반 카메라 이동에 필요한 범위에서 문제 없이 동작했고, 지금까지 DirectX를 직접 다뤄야 할 이유는 발생하지 않았다. 따라서 DirectX와 HLSL은 계속 deferred 상태로 둔다.

- 구현 위치: `src/` (`main.cpp`, `Player.*`, `Input.*`, `Camera.*`)
- 회귀 테스트: `tests/`, CTest로 실행하며 외부 테스트 라이브러리를 추가하지 않았다
- 빌드 확인 환경: Visual Studio 2022 17.13, 번들 CMake 3.30.5, MSVC 19.43, Windows SDK 10.0.22621

이 항목은 여전히 최종 기술 결정이 아니다. 배경과 되돌릴 조건은 [`decisions/0001-prototype-tech-stack.md`](decisions/0001-prototype-tech-stack.md)에 기록했다.

### 이동과 공중 행동 가설

이동 자체를 핵심 재미로 삼고, 작은 2D 로봇형 아바타를 현재 플레이어 표현 후보로 검토한다. 로봇형 디자인과 종족은 미확정이며 최초 콘셉트 아트의 캐릭터 표현을 대체하는 확정안이 아니다.

- 기본 이동 후보는 걷기, 달리기, 점프, 8방향 공중 대쉬, 체공, 급강하, 매달리기, 벽타기 또는 벽 슬라이드, 지상 슬라이드다.
- 달리기는 별도 키보다 같은 이동 방향을 빠르게 두 번 입력해 진입하고, 방향을 유지하는 동안 감속 없이 일정한 최고속도까지 계속 가속하는 방식을 우선 검토한다. 더블탭의 조작감과 가속·감속 규칙은 프로토타입에서 검증한다.
- 2단 점프를 두지 않고 8방향 공중 대쉬를 공중 이동의 핵심 수단으로 사용하는 방향을 우선 검토한다.
- 공중 대쉬는 횟수 1회로 제한하지 않고, 입력과 자원이 허용하는 동안 연속 사용 가능하게 하는 가설을 검증한다.
- 위 입력은 실제 상승보다 중력을 줄여 낙하를 억제하는 체공으로, 아래 입력은 빠른 낙하 또는 조건부 급강하로 연결하는 방식을 검토한다.
- 체공과 급강하가 이동 규칙을 과도하게 복잡하게 만드는지는 작은 조작 프로토타입으로 판단한다.

#### 2026-09-09 프로토타입 검증 결과

임시 사각형으로 아래 항목을 구현하고 Windows에서 실행해 사람이 직접 조작해 확인했다. 아래 수치는 모두 플레이 테스트용 후보값이며 확정 사양이 아니다.

| 항목 | 상태 | 현재 후보값 |
| --- | --- | --- |
| 걷기 | 구현·조작 확인 | `moveSpeed` 260px/s |
| 달리기 | 구현·조작 확인 | `runMaxSpeed` 440px/s, `runAcceleration` 600px/s² |
| 점프 | 구현·조작 확인 | `jumpSpeed` 520px/s, `gravity` 1500px/s² |
| 8방향 공중 대쉬 | 구현·조작 확인 | `dashSpeed` 700px/s, `dashDuration` 0.14s, `dashGravityScale` 0 |
| 연속 공중 대쉬 | 구현·조작 확인 | 횟수 제한 없음, 대쉬 중 재발동만 차단 |
| 벽 슬라이드 | 구현·조작 확인 | `wallSlideSpeed` 90px/s |
| 벽 접촉 후 점프 재사용 | 구현·조작 확인 | 수평 반동 없이 위로 재점프 |
| 체공 (`SlowFalling`) | 구현·조작 확인 | 위 홀드 시 낙하 속도를 `slowFallMaxSpeed` 120px/s로 제한 |
| 급강하 (`FastFalling`) | 구현·조작 확인 | 아래 홀드 시 중력에 `fastFallAcceleration` 3000px/s² 추가, `fastFallMaxSpeed` 1200px/s |
| 달리기 관성 점프 | 구현·조작 확인 | 같은 방향 유지 시 점프 직전 수평 속도 보존 |

가설과 관련해 확인한 것과 아직 열려 있는 것은 다음과 같다.

- 더블탭으로 달리기에 진입하고 방향을 유지하는 동안 최고속까지 가속하는 방식은 실제로 동작한다. `doubleTapWindow`는 0.25초를 쓰고 있으며, 이 값이 적절한지는 더 많은 조작 시간이 필요하다.
- 같은 더블탭 입력을 지상에서는 달리기로, 공중에서는 대쉬로 분기시켰다. 입력 계층은 접지 상태를 모르고 더블탭 신호만 내보내며, 분기는 플레이어 쪽에서 한다. 체공과 급강하를 붙일 때도 이 구조를 바꾸지 않아도 되는지 확인했고, 입력 계층을 수정하지 않고 추가할 수 있었다.
- 위아래 입력은 두 번 빠르게 누르면 대쉬, 계속 누르고 있으면 체공 또는 급강하로 갈린다. 홀드는 더블탭 신호를 만들지 않으므로 둘이 서로를 방해하지 않는다. 대쉬가 우선하고, 대쉬가 끝난 뒤 홀드가 유지되어 있으면 그때 낙하 모드로 들어간다.
- 체공은 상승을 만들지 않고 하강 속도만 제한한다. 벽에 붙어 있을 때는 급강하보다 벽 슬라이드를 우선하도록 두었다. 벽에서도 급강하를 허용할지는 아직 정하지 않았다.
- 달리기 중 점프하면 수평 속도를 잃던 문제를 고쳤다. 공중에서 걷기 속도로 덮어쓰지 않도록 한 것이 전부이며, 공중 이동 모델과 별도 상수는 추가하지 않았다.
- 2단 점프 없이 8방향 공중 대쉬를 공중 이동의 핵심 수단으로 두는 방향은 유지하고 있다.
- 벽 접촉으로 점프가 회복되므로 벽을 타고 연속으로 올라가는 이동이 가능하다. 현재는 이를 막지 않고 의도된 실험 기능으로 두고 관찰한다. 이 이동이 지나치게 강력한지는 지형이 늘어난 뒤에 판단한다.
- 달리기 중 점프하면 수평 속도를 유지하지 않고 즉시 일반 공중 제어 속도로 돌아간다. 관성을 남길지는 아직 정하지 않았다.
- 대쉬가 끝나는 순간 수평 속도가 관성 없이 즉시 바뀐다. 조작감에 문제가 되는지는 더 확인해야 한다.
- 위쪽 대쉬가 끝난 뒤에도 잠시 솟구치는데, 이 구간이 점프와 같은 상승 상태로 판정된다. 설계한 것이 아니라 대쉬 중 무중력과 상승 판정이 만나 생긴 결과다. 사람이 플레이해 보니 대쉬와 점프가 하나의 상승 동작처럼 읽혀 더 자연스러웠고, 고치지 않기로 했다. 배경은 [`decisions/0006-upward-motion-is-jumping.md`](decisions/0006-upward-motion-is-jumping.md)에 기록했다.

#### 2026-09-09 카메라

이동 검증을 위해 화면보다 넓은 practice room과 follow camera를 함께 만들었다. 카메라는 `sf::View` 하나를 옮기는 수준이며 별도의 카메라 프레임워크를 만들지 않았다.

- 수평은 플레이어를 직접 따라가고, 수직은 화면 중앙의 dead-zone(`verticalDeadZone` 240px)을 벗어날 때만 따라간다.
- 추적은 `1 - exp(-cameraFollowSpeed * dt)` 형태의 지수 감쇠를 쓰며 `cameraFollowSpeed`는 6/s다. 프레임레이트에 의존하지 않는다.
- 일반 점프의 최대 상승은 약 90px로 dead-zone 반경 120px 안에 들어오므로, 작은 점프로는 화면이 움직이지 않는다.
- 카메라는 월드 경계 밖의 빈 공간을 보여주지 않도록 X와 Y 모두 clamp한다.
- 급강하 중이거나 하향 속도가 700px/s를 넘으면 세로 추적 속도를 2.5배로 올린다. 같은 지수 감쇠 형태를 그대로 쓰므로 화면이 즉시 붙지 않고, 급강하가 끝나면 기본 속도로 돌아간다.
- 배경 이미지, parallax, 화면 흔들림, 줌은 넣지 않았다.

#### 2026-09-09 이동 상태 모델

이동 기능이 늘면서 조건문만으로 현재 상태를 파악하기 어려워져 명시적인 이동 상태를 도입했다. `Idle`, `Walking`, `Sprinting`, `Jumping`, `Falling`, `AirDashing`, `WallSliding`, `SlowFalling`, `FastFalling`을 두고 결정은 한 함수에서만 한다.

상태는 물리 사실을 대체하지 않는다. 접지 여부, 벽 접촉, 속도, 위치는 그대로 실제 데이터로 남고 상태는 그 값과 입력으로 정해진다. 현재 상태는 창 제목에 실시간으로 표시해 코드 밖에서 확인할 수 있다. 배경과 되돌릴 조건은 [`decisions/0003-movement-state-model.md`](decisions/0003-movement-state-model.md)에 기록했다.

향후 애니메이션, 파티클, 사운드, 카메라 반응, 멀티플레이 표현이 이 상태를 참조할 수 있는지는 실제로 붙여 본 뒤에 판단한다.

### 공중 행동 자원 가설

공중 대쉬와 체공에는 임시 명칭 `Air Charge`인 별도 공중 자원을 사용하는 방식을 검토한다. 명칭과 수치, UI는 미확정이다.

- 공중 대쉬는 사용 시 일정량을, 체공은 유지하는 동안 지속적으로 자원을 소모한다.
- 급강하는 무료 또는 낮은 비용으로 두는 방안을 검토한다.
- 자원이 소진되면 일반 중력과 제한적인 공중 제어만 허용하는 방안을 검토한다.
- 회복 방식은 2026-09-11에 방향을 바꿨다. 다른 플레이어와의 상호작용을 **유일한** 회복 수단으로 두면 혼자 하는 탐험이 막힌다. 그래서 혼자서도 언제든 회복할 수 있는 수단을 기본으로 두고, 협력 회복은 그 위에 얹는 보너스로 둔다.
- 혼자 회복하는 방식의 현재 후보는 지면에 있는 상태에서 아래 방향키를 약 1초 유지하는 것이다. 충전하는 동안 잠시 머물게 하면서도 혼자서 언제든 다시 출발할 수 있다. 수치와 입력은 미확정이다.
- 위 후보는 나중에 아래 입력을 한 방향 통과 발판에 쓰게 되면 충돌한다. 확정할 때 함께 검토한다.
- **구현 시점을 뒤로 미룬다.** 이동을 제한하는 것이 이 게임의 재미가 아니므로, 넓은 공간에서 떠다니는 감각을 먼저 만들고 자원은 그 뒤에 얹는다. 지금 자원을 넣으면 아직 만들지도 않은 공간을 기준으로 수치를 정하게 된다.

### 멀티플레이와 상호작용 가설

멀티플레이는 경쟁보다 협력과 부담 없는 우연한 조우를 중심으로 한다. 첫 멀티플레이 프로토타입은 최대 2인을 우선 고려하지만 최종 인원은 미확정이다.

- 복잡한 파티 시스템이나 채팅에 의존하지 않아도 의미가 전달되는 단일 상호작용 입력을 검토하며, 기본 키 후보는 `F`다.
- `F`를 짧게 누르면 가까운 범위에 원형 파동을 즉시 방출하고, 하트 또는 짧은 빛 효과와 함께 주변 플레이어의 공중 자원을 회복시키는 방안을 검토한다.
- `F`를 길게 누르면 누르는 동안 범위가 확장되고, 키를 놓는 순간 확장된 범위에 파동을 방출하는 방안을 검토한다. 구체적인 범위, 충전 시간과 회복량은 미확정이다.
- 장거리 상호작용은 공중 자원이 소진되어 추락하는 플레이어에게 자원을 전달하고, 다시 대쉬해 복귀할 기회를 주는 구조 상황을 만들 수 있다.
- 악수나 포옹처럼 캐릭터별 직접 애니메이션을 늘리기보다 원형 파동, 하트와 짧은 빛 등 공통 이펙트 중심으로 표현하는 방안을 검토한다.
- 두 플레이어가 서로 동시에 상호작용하면 일방 상호작용보다 큰 회복 또는 임시 `Resonance` 상태를 제공하는 가설을 검토한다. 명칭, 동시 판정 시간과 효과는 미확정이다.
- 이 단일 입력은 상황에 따라 안녕, 감사, 격려, 존재 알림, 전달과 구조의 의미를 플레이어가 스스로 부여할 수 있게 하는 것을 의도한다.
- 기존 거리 기반 근접 채팅은 별도의 가설로 유지한다. `F` 상호작용은 채팅이 없거나 사용되지 않는 상황에서도 핵심 협력이 가능해야 한다는 가설이다.

### 공중 급유와 지상 교류 가설

다른 플레이어와의 상호작용으로 공중 자원을 회복하는 개념을 개발 중 임시로 `공중 급유`라고 부른다. 이 가설은 다른 플레이어의 존재를 이동 시스템 자체에 의미 있게 연결하는 것이 목적이다.

- 혼자서도 대부분의 일반 지역을 탐험할 수 있고, 다른 플레이어가 없어도 진행이 막히지 않아야 한다.
- 두 플레이어가 협력하면 더 오래 비행하고, 공중 급유를 반복하면 이론적으로 매우 긴 시간 동안 공중 이동할 수 있는 가능성을 검토한다.
- 높은 장소나 특수 경로는 협력 시 더 쉽게 접근할 수 있지만, 일반 탐험에 다른 플레이어를 강제하지 않는 방향을 우선한다.
- 공중에서는 급유, 추락 구조와 하트 신호처럼 짧고 순간적인 만남을 지향한다.
- 지상에서는 현재 검토 중인 악기 연주와 모닥불을 통해 잠시 머물 이유와 느리고 지속적인 교류를 만드는 방향을 검토한다.
- 강제 파티, 고정 역할 분담, 음성 채팅 의존, 복잡한 이모트 휠과 경쟁 중심 PvP는 최소화하는 방향을 검토한다.
- 2인 장치는 진행을 막는 잠금이 아니라 보너스로 둔다. 현재 후보는 둘이 함께 밟으면 열려 보너스 공간으로 이어지는 문, 한 명이 안쪽에서 열어 주는 지름길, 협주에 반응하는 환경, 함께 있을 때만 나타나는 시각·음악 이벤트 정도다.
- 상대에게 공중 자원을 나눠 주어 더 오래 떠 있게 하는 것도 같은 성격이다. 없으면 못 가는 곳을 만들기 위한 장치가 아니다.

공중은 "서로를 살려주며 스쳐 지나가는 공간", 지상은 "함께 잠깐 머무는 공간"이라는 대비를 현재 경험 가설로 둔다.
