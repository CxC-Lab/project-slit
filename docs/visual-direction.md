# Project Slit 비주얼 방향

![Project Slit 최초 게임플레이 콘셉트](../assets/concept-art/project-slit-gameplay-concept-v001.png)

이 문서는 최초 게임플레이 콘셉트 아트에서 읽을 수 있는 방향과 향후 검증할 질문을 기록한다. 이미지는 최종 게임 화면이나 확정된 구현 사양이 아니다.

## 이미지에서 읽을 수 있는 방향

- 2D 사이드뷰 기반의 횡방향 탐험
- 캐릭터보다 압도적으로 큰 폐허와 구조물
- 전경, 중경, 원경 레이어를 이용한 깊이감
- 경사면과 다층 플랫폼이 연결된 이동 공간
- 작고 귀여운 플레이어 캐릭터와 거대한 세계의 대비
- 비, 무지개, 안개와 같은 날씨와 대기 표현
- 따뜻한 황금빛 하늘과 주홍빛 식생
- 화면을 압도하는 수직 구조와 멀리 이어지는 이동 가능 공간
- 플레이어가 제한된 수만큼 보유하고 월드에 설치하는 깃발
- 멀리 있는 다른 플레이어와 말풍선으로 표현된 가벼운 조우
- 목적지나 퀘스트보다 이동과 발견 자체를 강조하는 경험

## 이 이미지로 확정하지 않는 사항

- 최종 픽셀 크기와 화면 해상도
- 캐릭터의 최종 디자인과 종족
- 실제 UI 배치와 깃발 아이콘
- 특정 색상 팔레트
- 타일 크기와 충돌 구조
- 배경 레이어의 실제 개수
- DirectX와 HLSL의 구체적인 렌더링 방식
- 후처리와 날씨 효과의 구현 방법
- 지역의 최종 설정과 스토리
- 이미지에 표현된 모든 구조물이 실제로 이동 가능한지 여부

## 구현 과정에서 검증할 질문

- 작은 캐릭터가 복잡한 배경에서도 명확하게 보이는가?
- 장거리 이동 중 배경 변화가 반복적으로 느껴지지 않는가?
- 거대한 수직 구조물이 실제 이동 경로와 자연스럽게 연결되는가?
- 비와 후처리가 플레이 가독성을 방해하지 않는가?
- 깃발과 다른 플레이어의 말풍선이 배경보다 과도하게 튀지 않는가?
- 패럴랙스와 다중 레이어 구성이 성능 목표를 만족하는가?
- 콘셉트의 화면 밀도를 유지하면서 충돌 지형은 단순하게 구성할 수 있는가?

## 플레이어 아바타와 스프라이트 정책 가설

작은 SD 비율의 2D 로봇형 픽셀 아바타를 우선 검토한다. 다수의 사전 제작 아바타 중 선택하는 방식을 우선하며, 초기 상한 후보는 최대 64종이지만 수량은 미확정이다. 런타임 생성형 AI로 아바타를 직접 만드는 방식은 현재 우선순위가 낮고, AI는 개발 중 캐릭터 시안과 에셋 제작을 보조할 수 있다.

외형이 다른 아바타도 동일한 animation state 이름, 프레임 캔버스와 atlas index 규칙을 공유하는 방향을 검토한다. 초기에는 한 종으로 전체 규격을 검증하며 64종을 먼저 제작하지 않는다.

### 프레임 캔버스

- 모든 아바타와 애니메이션 프레임에 동일한 고정 크기 PNG 캔버스를 사용하는 방향을 우선 검토한다.
- 동작에 따라 실제 캐릭터 외곽 크기가 달라도 프레임 크기를 바꾸거나 매 프레임 외곽선에 맞춰 crop하지 않는다.
- 캐릭터가 작은 프레임에는 투명 여백을 허용한다.
- 캔버스 크기 후보는 `64x64`, `96x96`, `128x128`이며 실제 아트와 가독성 테스트 후 결정한다.

### Pivot과 visual offset

- 모든 프레임은 기본적으로 프레임 중앙 X와 바닥에 닿는 발 위치 Y를 공통 pivot으로 사용하는 방향을 검토한다.
- Idle, Walk, Run과 Jump에서 실루엣 크기가 달라도 pivot은 유지하며, 렌더링은 pivot을 기준으로 배치한다.
- 프레임마다 캐릭터 그림을 가운데 정렬하지 않는다.
- 매달리기나 벽타기처럼 손 또는 벽 접촉점이 중요한 동작도 기본 pivot을 유지하는 방향을 우선 검토한다.
- 필요한 경우 애니메이션 또는 프레임별 `visualOffset`을 렌더링 보정에만 사용한다. 예를 들어 `visualOffset = (+2, -1)`은 그림만 이동하며 플레이어의 월드 좌표나 물리 위치를 바꾸지 않는다.

### 렌더링과 물리의 분리

다음 상태를 서로 독립적으로 관리하는 구조를 지향한다.

- player world position
- velocity
- collider
- sprite
- animation state
- visual offset

검이나 장식물이 멀리 뻗거나 점프·슬라이드 중 실루엣이 달라져도 이미지 외곽만으로 collider를 바꾸지 않는다. 물리 상태의 변화가 필요하다면 스프라이트 프레임과 별도 규칙으로 처리한다.

### 애니메이션 프레임 수

부드러운 다프레임 표현보다 작은 픽셀 캐릭터에서도 읽히는 짧고 명확한 2~3프레임 애니메이션을 기본 가설로 둔다. 이는 다수 아바타의 제작 비용과 AI 보조 제작 시 프레임 불일치를 줄이기 위한 방향이며, 정확한 수는 테스트 후 변경할 수 있다.

| Animation state | 프레임 수 후보 |
| --- | ---: |
| Idle | 2 |
| Walk | 2~3 |
| Run | 2~3 |
| Jump | 1~2 |
| Fall | 1~2 |
| Air Dash | 2 |
| Hover | 1~2 |
| Fast Fall / Dive | 1~2 |
| Wall Slide / Wall Climb | 2~3 |
| Hang | 2 |
| Ground Slide | 2 |
| Music | 2 |

### 음악 연주 애니메이션

- 기타, 피아노, 피리 등 악기마다 캐릭터 애니메이션을 새로 만들지 않고 `Music Idle`과 `Music Play` 같은 공통 본체 애니메이션을 우선 검토한다.
- 악기 외형은 캐릭터가 직접 드는 방식보다 캐릭터 앞에 펼쳐지거나 몸에 부착되는 공통 연주 장치로 표현하는 방향을 검토한다.
- 악기별 차이는 MIDI instrument 또는 patch, SoundFont와 음색을 중심으로 표현하고 필요할 때 소형 이펙트나 장치 색상을 보조적으로 사용한다.
- 목적은 아바타 수와 악기 수의 곱만큼 애니메이션이 늘어나는 것을 방지하는 것이다.

### 스프라이트 시트와 검증 규칙

모든 Avatar ID가 동일한 animation state 이름과 atlas index 규칙을 공유해야 한다. 행 구성 후보는 Idle, Walk, Run, Jump/Fall, Air Dash/Hover, Fast Fall, Wall/Hang, Slide, Music 순이지만 정확한 행·열 배치는 미확정이다.

AI 또는 수작업으로 제작한 아바타는 적용 전에 다음을 검증한다.

- 모든 프레임의 canvas size와 pivot 위치가 같은가?
- 발 위치가 애니메이션 중 불필요하게 흔들리지 않는가?
- 프레임 사이에서 캐릭터 전체 크기가 급격하게 변하지 않는가?
- 좌우 방향 전환 시 실루엣 문제가 없는가?
- 투명 배경이 유지되는가?
- 작은 보정을 `visualOffset`으로 처리할 수 있는가?
- collider와 sprite가 독립적으로 동작하는가?

제작 규격은 테스트 아바타 한 종으로 Idle/Walk/Run, Jump/Air Dash, Wall/Slide, Music 순서로 검증한다. pivot과 프레임 규격이 안정된 뒤에만 2~4종을 추가하고, 교체 가능성이 확인된 이후 아바타 수를 확대한다.
