# Avatar Lake `inner` — 원본 형태 역수입 실험 보고서

이전 단계(팔레트 추출 후 컬럼 공식으로 재구성한 `rock_inner_01/02.png`, 40×40 2×2 phase 실험)는
그대로 보존했습니다. 이 문서는 그것을 대체하는 별도 실험(`build/preview/avatar_lake/tiles/raw_import_experiment/`)의
결과입니다. 게임 코드, `avatar_lake.json`, 기존 에셋은 건드리지 않았고 커밋하지 않았습니다.

## 0. 왜 이전 결과를 그대로 쓰면 안 되는가 — 실패 원인 재확인

이전 도구(`normalize_avatar_lake_tiles.cpp`)는 원본에서 **팔레트만** 뽑고 무늬는 20×20 안에서
컬럼 공식으로 **새로 그렸습니다**. 그 결과 원본에 있던 다음 특징이 전부 사라졌습니다.

- 넓고 불규칙한 암반 덩어리 → 폭이 똑같은(6,6,4px) 컬럼 3개로 대체됨
- 위치마다 다른 암층 폭 → 모든 컬럼이 같은 공식으로 생성돼 폭이 균일함
- 비대칭적인 하이라이트/그늘 → 매 컬럼 동일 위치(오른쪽 끝 2px)에 하이라이트가 반복됨

`repeat_comparison/A_current_20x20_x2.png`와 `repeat_comparison/B_macro_80_shapepreserving_x2.png`를
나란히 놓고 보면 차이가 명확합니다 — A는 여전히 바코드/회로기판처럼 보이고, B는 실제 암반으로 보입니다.

## 1. 역할 수 vs raw 원본 수 — "나머지 8개"라는 표현 정정

**제 실수였습니다.** 이전 `normalization_report.md`의 13절 제목을 "나머지 **8개** 역할"이라고 썼는데,
실제로는 10개 역할에서 `inner`를 뺀 **9개**(`top, bottom, left, right, top_left, top_right,
bottom_left, bottom_right, slab`)가 맞습니다. 표에는 9개 행이 다 있었는데 제목 숫자만 잘못 셌습니다 —
특정 역할을 의도적으로 제외한 것이 아니라 단순 계산 실수였습니다. 정정합니다.

**역할 수(10, `inner` 제외 시 9)와 실제로 필요한 raw 원본 수는 다른 질문입니다.**
`tools/generate_tileset.cpp`의 진단용 아틀라스 생성 로직을 보면 역할이 두 축의 조합으로 분해됩니다.

```cpp
const bool top=role==1 || role==5 || role==6 || role==9;     // top, top_left, top_right, slab
const bool bottom=role==2 || role==7 || role==8 || role==9;  // bottom, bottom_left, bottom_right, slab
const bool left=role==3 || role==5 || role==7;                // left, top_left, bottom_left
const bool right=role==4 || role==6 || role==8;                // right, top_right, bottom_right
```

즉 4개 모서리는 "위/아래 노출 + 좌/우 노출"의 조합이고, `slab`은 "위+아래 노출, 좌우 없음"입니다.
이 구조를 근거로 답하면:

1. **10개 역할마다 별도 raw가 필요하지는 않습니다.** 다만 이는 "회전으로 파생"이 아니라 "반전(mirror)과
   조합(composite)"으로 파생 가능하다는 뜻입니다 — Avatar Lake는 위쪽만 풀/흙이 있고 좌/우/아래는 노출된
   암반이라는 전제가 유지된다면(이번 두 원본이 보여주는 "풀 없는 암반 내부"와 일치):
   - `left`와 `right`는 **같은 "측면 절단" raw 1장을 좌우 반전**해서 만들 수 있습니다(암반 절단면은 좌우
     비대칭성이 중요하지 않음).
   - `bottom`은 측면 절단 raw를 재활용할 수도 있지만, 아래쪽은 보통 그늘(햇빛이 안 닿음)이라 색조가
     달라야 할 가능성이 높습니다 — **미술적 판단이 필요**합니다(회전/반전만으로 충분한지, 별도 raw가
     필요한지는 아트 리뷰 대상).
   - 4개 모서리는 "top-edge 조각 + side-edge 조각을 이어붙이는" 조립으로 **1차 근사**는 가능하지만,
     decision 0009가 이미 지적했듯("모서리 역할의 아트는 실제 충돌 경계에 붙는다") 자연스러운 모서리는
     보통 전용 아트가 더 낫습니다. 프로토타입 단계이므로 조립 결과로 먼저 검증하고, 어색하면 그때 전용
     raw를 추가하는 순서를 권장합니다.
   - `slab`은 "위 조각 + inner 조각 + 아래 조각"을 세로로 쌓아 조립기로 만들 수 있을 가능성이 높습니다
     (한 칸 높이 발판이라 세 조각을 쌓는 구성 자체가 이미 decision 0009의 정의와 일치).
2. **현재 조립기는 존재하지 않습니다.** `right`/모서리/`slab`을 자동으로 파생하는 코드나 도구는 아직
   없습니다 — 필요하면 새로 만들어야 합니다(이번 두 실험 도구와 비슷한 성격의 오프라인 도구가 될 것).
3. **결론(질문 9의 답):** 최소 시나리오로는 `top`용 raw 1장 + `side`(좌우 겸용, 아래에도 재사용 가능할지
   미술 검토 필요)용 raw 1장, 총 **2장** 추가로 9개 역할을 커버할 가능성이 있습니다. 아래(`bottom`)와
   모서리가 조립만으로 부족하다고 판단되면 최대 **4~5장**(측면과 별도로 `bottom` 전용, 모서리 전용 1~2장)
   까지 늘 수 있습니다. **정확한 숫자는 아트 리뷰 없이 확정할 수 없고, 이번 단계에서 결정하지 않습니다.**

## 3. 원본 역수입 절차 (실제로 한 것)

`tools/raw_import_experiment.cpp` (신규, `EXCLUDE_FROM_ALL`, 게임 빌드에 포함 안 됨):

1. **최근접 이웃 다운샘플** (`downsampleNearest`): 목표 해상도의 각 픽셀이 원본의 대응 좌표를 그대로
   점 샘플링합니다. 평균/블러 없음 — 원본의 실제 배치를 그대로 축소만 합니다.
2. **14색 팔레트로 양자화**: 이전(6색)보다 넉넉하게 잡아 암반/그늘/하이라이트를 뭉개지 않고 유지.
   안티에일리어싱 픽셀은 이 단계에서 팔레트 색 중 하나로 이산화됩니다.
3. **toroidal offset**: 크롭된 이미지를 캔버스 절반만큼 랩어라운드 이동. 원본 크롭 자체의 좌우/상하
   경계는 원래 서로 안 맞물리므로(애초에 만들 때 반복을 고려하지 않은 이미지), 이 이동으로 두 경계를
   전부 캔버스 중앙의 십자 모양으로 옮깁니다.
4. **중앙 이음선 최소 보정**: 그 십자 부근 픽셀만 5×5 이웃 평균을 내서 같은 팔레트로 재양자화합니다.
   이미지의 나머지 부분(대부분)은 원본 크롭 그대로입니다 — "seam 고친다고 전체를 다시 그리는" 일은
   하지 않았습니다.

## 4. 정직한 결과: 이음선 보정 자체에 새로운 흠이 생겼습니다

`macro_01_80_seamless_inspect.png`를 직접 보면, 중앙 보정 부위가 **부드럽게 흐려진 십자 얼룩**으로
눈에 띕니다 — 주변의 또렷한 픽셀아트와 대비돼 오히려 새로운 결함처럼 보입니다. `seam_metrics.md`
수치도 이를 뒷받침합니다.

- **크롭 자체의 원래 좌우/상하 경계**는 생각보다 이미 나쁘지 않았습니다(01_80: h=6.75, v=7.12/255).
- 반면 offset이 만든 새 경계(=원본 크롭의 중간 지점)는 오히려 더 컸습니다(01_80: h=21.87/255) —
  우연히 크롭 중앙에 색 대비가 큰 경계(밝은 암층↔그늘)가 있었기 때문입니다.
- 보정 후에도 완전히 회복되지 않았고(16.68/255), 그 대신 앞서 말한 흐린 얼룩이 생겼습니다.

그래서 **비교용으로 "offset/보정을 전혀 하지 않은 순수 크롭"도 만들어 확인**했습니다
(`repeat_comparison/E_plain_crop_no_offset_no_repair_x2.png`). 놀랍게도 이 순수 크롭을 그대로
반복해도 **눈에 띄는 하드 이음선이 보이지 않습니다** — 텍스처 자체가 방향성 있는 노이즈가 많아
경계가 통계적으로 비슷해 보이기 때문으로 추정됩니다.

**결론: 이번 실험 결과, `toroidal offset + 중앙 보정`은 필요하지 않았을 가능성이 높고, 오히려 손해였습니다.**
`E`(순수 크롭)를 `B`(offset+보정)보다 더 나은 기본안으로 제안합니다. 다만 이는 이번 두 원본에서
우연히 그런 것일 수 있으므로, 나중에 실제로 이 원본을 변형하거나 새 raw를 추가할 때는 매번 크롭 경계를
다시 확인해야 하며 "offset+보정"이라는 방법 자체를 폐기할 필요는 없습니다(다른 원본에서는 필요할 수
있음) — 이번에 만든 도구(`toroidalOffset`, `repairCenterSeam`)는 기록으로 남기되, 기본 채택안은 아닙니다.

## 6. 좌표계 검토

- **컴포넌트 로컬 좌표를 권장합니다.** decision 0009가 "연결된 덩어리는 하나의 격자를 공유한다"고
  이미 정했고, 매크로 텍스처 샘플링도 이 계약을 따라야 합니다. 절대 월드 좌표를 쓰면 같은 지형을
  나중에 다른 위치로 옮기기만 해도(현재 지형은 README에 "연습용 초안"이라 명시) 매크로 무늬가 밀려
  보이는 부작용이 생깁니다.
- **음수 좌표 나머지 연산 주의**: 컴포넌트 bounds.position이 음수인 경우(`avatar_lake.json`의 solids에는
  y가 -4800까지 내려가는 값이 실제로 있습니다), `(cell - origin)`은 항상 0 이상이 되도록 설계할 수
  있지만, 매크로 텍스처 자체의 크기(80 또는 120)로 한 번 더 wrap해야 한다면 C++의 `%`는 음수에 대해
  음수를 반환하므로 `((n % m) + m) % m` 형태로 감싸야 합니다. 이번 오프라인 도구의 `toroidalOffset`은
  전부 양수 좌표만 다뤄 이 문제를 실제로 겪지 않았습니다 — 실제 구현 시 별도 테스트가 필요한 지점으로
  남겨둡니다.
- **아틀라스 인접 셀 bleed**: `inner`를 기존 10-role 아틀라스에서 분리하면, nearest-neighbor 샘플링이
  아틀라스의 다른 역할/변형 칸을 침범할 위험 자체가 사라집니다(매크로 텍스처가 다른 역할과 같은 파일에
  있지 않으므로) — 이 점에서도 분리가 더 단순합니다.

## 8. 판정 기준 대조

- 바코드/회로기판처럼 보이지 않는가 → **B/D/E 모두 그렇지 않음.** A만 해당.
- 20/40px 간격의 규칙적 줄무늬 → 없음(암층 폭이 30~90px 대로 불규칙, 2절 분석과 일치).
- 원본의 암반 형태 보존 → 보존됨(다운샘플이 점 샘플링이라 원본 배치를 그대로 축소).
- Avatar Lake 원경과 같은 세계로 보이는가 → `scene_mockup_1920x1080.png`에서 배경 절벽과 색감·질감이
  잘 어울립니다.
- 원경보다 전경이 읽히되 튀지 않는가 → 이전 단계에서 실측한 팔레트 대비 조정(밝기/대비)은 이번
  raw-import 팔레트에는 다시 적용하지 않았습니다 — **아직 검증되지 않은 항목**입니다(아래 열린 질문).
- 플레이어 실루엣/이동 경로 방해 → mockup에서 proto_one이 잘 보이고 텍스처가 캐릭터보다 튀지 않음.
- 큰 플랫폼 내부에 반복 도장 무늬 → E(순수 크롭) 기준 `repeat_comparison`에서 눈에 띄는 도장 무늬 없음.
- 셀 경계를 숨긴 상태에서 20×20 격자가 드러나는가 → `_grid.png`/무그리드 버전 비교 결과, 격자가
  드러나지 않음(매크로 이미지 자체가 연속이므로).
- 향후 top/side/bottom과 연결 가능한가 → 1절에서 다룬 대로, 좌우/상하 조합 관계가 성립할 여지가
  있으나 아트 검토가 필요.
- 구현 복잡도가 프로젝트 규모에 비해 과도한가 → 5·6절 정리한 변경 범위(Tileset 필드 1개, `pieces()`
  분기, 좌표 wrap 유틸 함수 1개, 테스트 갱신)는 크지 않다고 판단합니다 — 다만 "언제 할 것인가"는
  이번 보고 대상이 아닙니다.

## 9. 결론 — 10가지 질문에 대한 답

1. **inner를 기존 20×20 반복 타일로 유지할 수 있는가?** 저장 단위(파일 크기)는 20×20으로 유지할 수
   있지만, 그 안의 그림을 20×20 안에서 독립적으로 완결시키려는 시도(기존 절차)는 이번 실험으로도
   다시 실패를 재현할 뿐입니다(2절 분석: 큰 구조가 30~60px 폭). **그림 자체는 더 큰 매크로 텍스처의
   일부여야 합니다.**
2. **원본 형태를 보존한 매크로 텍스처가 필요한가?** 예 — B/D/E가 A를 압도적으로 능가합니다.
3. **적절한 크기는 40/80/120?** 40은 부족(이전 실험과 이번 분석 모두 일치), **80을 기본으로 권장**,
   120은 여유 후보(약간 더 다양하지만 저장/관리 비용 증가). 실제 채택 전 아트 리뷰 필요.
4. **10-role atlas와 inner macro texture 분리가 적절한가?** 예 — 기존 아틀라스의 고정 그리드
   치수 검증(`TerrainTiles.cpp:163`)과 구조적으로 맞지 않아 분리가 더 단순합니다.
5. **world vs component-local?** component-local 권장(decision 0009의 "공통 격자" 계약과 일치).
6. **`tileHash(cell,seed)`를 inner에 계속 쓸 수 있는가?** 아니오 — 매크로 방식에서는 "변형 선택"이
   아니라 "연속 좌표 샘플링"이 되므로 해시 기반 변형 슬�립 개념 자체가 `inner`에는 더 이상 맞지 않음.
7. **quiet base + macro decoration 분리가 더 적절한가?** 이번 실험(D)에서 가장 깔끔한 실루엣을
   보였습니다. 다만 "진짜 2-레이어 합성"으로 만들지, 매크로 텍스처 자체를 이렇게 디자인할지는 렌더
   비용 대 재사용성을 따져 별도 결정이 필요합니다.
8. **코드/테스트 변경 범위?** 5·6절 요약 참고 — `Tileset`에 macro 경로 필드, `pieces()`의 `inner`
   전용 분기, 좌표 wrap 유틸리티, `TerrainTilesTests.cpp`의 시드/변형 관련 테스트 갱신.
9. **9개 역할(10 - inner) 중 실제로 별도 raw가 필요한 것은?** 최소 2장(top 1 + side 겸용 1)부터
   최대 4~5장까지 — 정확한 숫자는 아트 리뷰로 확정 필요(1절 참고). **"8개"라는 이전 표현은 단순
   계산 실수였습니다.**
10. **나머지 역할용 raw를 만들기 전에 확정할 계약은?** (a) inner의 최종 방식(20×20 유지 vs 매크로,
    크기), (b) 좌표계(component-local로 확정 권장), (c) quiet base/macro decoration 분리 여부,
    (d) "1 world unit = 1px" 가정이 실제 카메라 줌과 맞는지(이번 mockup은 이 가정을 썼으나
    `Display.cpp`/`Camera.cpp` 값으로 검증하지 않았습니다).
