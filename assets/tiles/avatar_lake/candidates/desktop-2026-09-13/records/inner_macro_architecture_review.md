## 1. 한 문단 결론

`E1_medium`을 지금 그대로 `assets/tiles/avatar_lake/normalized/rock_inner_01.png`로 승격해도,
**현재 코드로는 애초에 로드조차 되지 않습니다** — `TerrainTiles.cpp:163`의 아틀라스 치수 검증이
`아틀라스 너비 == max(variants)*tileSize(20)`을 강제하는데, E1은 80×80이라 이 등식이 깨지고
런타임 예외(`"Tileset image dimensions mismatch"`)로 즉시 실패합니다. 다만 이 문제의 해법은
이미 이 저장소 안에 검증된 선례가 있습니다 — `Background.cpp`가 `sf::Texture::setRepeated`로
좌표를 사람이 계산하지 않고 하드웨어가 반복 샘플링하게 만드는 패턴을 이미 쓰고 있고, 이를
`inner` 역할에 그대로 적용하면(컴포넌트 로컬 연속 좌표 + 하드웨어 반복, 변형은 셀이 아니라
컴포넌트 단위로 선택) 사람이 UV를 계산하는 일 없이 나머지 9개 역할과 공존할 수 있는 구조가
됩니다. 즉 **방향은 검증됐지만 그 방향을 구현하는 코드·스키마·재생성 도구는 아직 하나도
만들어지지 않았습니다.**

## 2. 판정: **CONDITIONAL GO**

E1을 실제 게임에 적용해도 되지만, 아래 3절의 최소 선행 조건(스키마 확장, `inner` 전용 연속-UV
경로, 컴포넌트 단위 변형 선택, 매니페스트 기반 재생성 도구 1개로 통합)을 먼저 마쳐야 합니다.
이 조건들은 전부 이 저장소의 기존 패턴(`Background.cpp`, `avatar_lake.json`의 데이터 기반 설계,
`proto_one.manifest.json`)에서 그대로 가져올 수 있어 "구조를 처음부터 새로 설계"하는 수준은
아닙니다 — 그래서 NO-GO가 아니라 CONDITIONAL GO입니다.

## 3. 권장 구조

**공통 원칙**: 모든 역할의 텍스처는 "컴포넌트 로컬 원점에 고정된, 하드웨어가 반복 샘플링하는
연속 좌표계"라는 하나의 개념으로 통일할 수 있습니다. 기존 10-role 아틀라스는 이 개념의 특수한
경우입니다 — 반복 주기가 정확히 tileSize(20)이고 여러 변형이 한 이미지 안에 나란히 미리 구워진
경우일 뿐입니다.

| 역할 | 반복 축 | 권장 방식 |
|---|---|---|
| `inner` | 가로+세로 모두 큰 주기 | **신규**: 별도 매크로 텍스처, 컴포넌트 로컬 연속 UV, `setRepeated(true)` |
| `top` / `bottom` | 가로만 큰 주기(경계선 방향) | `Background.cpp`의 `repeatX` 레이어와 동일한 패턴 재사용 가능 — 향후 검토 |
| `left` / `right` | 세로만 큰 주기 | 위와 대칭(`repeatY` 개념) — 향후 검토 |
| 모서리 4종, `slab` | 반복 없음(1회성 형태) | **기존 10-role 아틀라스 그대로 유지** — 변경 불필요 |

이 표가 답하는 것: 10개 역할에 10가지 서로 다른 특수 처리가 필요한 게 아니라, **"2D 매크로
반복 / 1축 매크로 반복 / 비반복 단일 타일"이라는 3가지 범주**로 정리됩니다. `Background.cpp`가
이미 `repeatX` 플래그 하나로 이 개념을 구현해 검증했으므로, 이번에 발명하는 개념이 아니라
기존 패턴을 재사용하는 것입니다.

**왜 이 구조인가 (대안 대비):**

- *완성 타일 방식(각 역할 이미지가 암반+경계를 모두 포함)*: E1의 스케일을 유지하려면 역할마다
  거대한 원본이 필요하고, 서로 다른 원본 사이 암반 색·무늬가 자연스럽게 안 이어질 위험이 큽니다.
- *공통 암반 재질 위에 경계만 얹는 방식*: 유망하지만 "얹는" 합성이 런타임 기능이 되어야 하는데,
  현재 렌더러는 단일 텍스처 샘플만 하므로 별도 렌더 패스나 셰이더가 필요 — 이번 단계엔 과함.
- *10-role 아틀라스를 유지한 채 inner만 분리 (권장)*: 코드 변경 범위가 가장 작고, 이미 검증된
  `Background.cpp` 패턴을 그대로 씁니다. 9개 역할은 전혀 안 건드립니다.
- *매크로 암반+작은 경계 타일을 "조립 단계"에서 결합*: 모서리/`slab`에는 필요할 수 있지만
  (5절 참고), `inner` 자체에는 조립이 필요 없으므로 과설계입니다.

## 4. 대안 구조 비교 표

| 기준 | 완성 타일 | 공통 재질+경계 합성 | **아틀라스 유지+inner 분리(권장)** | 매크로+조립 |
|---|---|---|---|---|
| E1 스케일 유지 | 가능(원본 커야 함) | 가능 | 가능 | 가능 |
| 색상/무늬 단절 방지 | 위험(원본마다 제작) | 좋음 | 좋음(같은 팔레트 계약 전제) | 좋음 |
| 에셋 교체 용이성 | 낮음 | 중간 | 높음(파일 하나 교체) | 중간(조립 재실행 필요) |
| 신규 지역 추가 | 매번 반복 | 매번 반복 | 재사용 가능(도구가 세계 이름만 받으면) | 재사용 가능 |
| 코드 예외 분기 | 역할마다 발생 | 셰이더/합성 로직 필요 | `inner` 1곳만 | `inner`+조립기 |
| 기존 충돌 기반 판정 유지 | 유지 | 유지 | **완전히 유지**(decision 0009 안 건드림) | 유지 |
| 아틀라스/테스트 관리 | 복잡 | 복잡 | 단순(9-role 아틀라스+1개 별도 파일) | 단순~중간 |

## 5. 10개 역할 공통 규칙과 예외

**공통 규칙**: 모든 역할은 (a) 연결 컴포넌트의 공통 격자 원점(decision 0009)을 UV 기준으로 삼고,
(b) nearest-neighbor, (c) tileSize를 JSON에서 읽는다는 원칙을 그대로 공유합니다. 이건 이미
지켜지고 있고 바뀌지 않습니다.

**예외(반드시 다른 처리가 필요한 지점)는 딱 하나**입니다 — `inner`만 "아틀라스 변형 선택"이 아니라
"연속 텍스처 샘플링"을 씁니다. 나머지 9개는 지금 코드 그대로(`tileHash(cell,seed)%variants[role]`)
유지합니다. 이는 "예외가 역할마다 늘어난다"는 최악의 시나리오와 다릅니다 — 예외는 **정확히 1개
역할, 1개 코드 분기**로 한정됩니다.

`top`/`bottom`/`left`/`right`를 나중에 1축 매크로로 바꾸고 싶어질 수 있지만(6절), 그건 **오늘
결정할 필요가 없고, 결정하지 않아도 `inner` 작업에 영향이 없습니다** — 독립적으로 나중에 검토
가능합니다.

## 6. 사용자 관점의 에셋 편집·재생성 흐름 평가

예시 명령들을 하나씩 평가합니다.

| 명령 | 선행 조건 충족 시 | 오늘 당장(선행 조건 전) |
|---|---|---|
| "inner 원본을 새 이미지로 교체" | 설정/에셋 교체만(매니페스트의 이미지 경로 변경 후 도구 재실행) | 새 .cpp 실험 파일을 또 만들어야 함(지금까지의 패턴) |
| "암반 무늬를 1.5배 크게" | 매니페스트의 크롭 비율 값만 변경 후 재생성 명령 1회 | 코드/스크립트를 손으로 고쳐야 함 |
| "top의 풀 두께를 2px 줄여라" | top 역할이 아직 정의 전이라 판단 불가 — 9절의 계약 확정 후 가능 | 불가 |
| "반복 프리뷰를 다시 생성" | 이미 가능(세 도구 모두 이 패턴을 잘 구현함) | 이미 가능 |
| "새 지역용 타일셋을 Avatar Lake 규격으로" | 도구가 세계 이름을 매개변수로 받으면 가능 | **불가** — 세 도구 모두 `assets/tiles/avatar_lake/...` 경로가 하드코딩돼 있음 |
| "기존 설정으로 되돌려라" | 매니페스트에 버전/이력이 있으면 가능 | **불가** — 되돌릴 대상을 추적하는 기계가 읽을 수 있는 기록이 없음(prose 보고서뿐) |

**핵심 관찰**: 지금까지 만든 세 도구(`normalize_avatar_lake_tiles.cpp`,
`raw_import_experiment.cpp`, `raw_import_scale_experiment.cpp`)는 각각 훌륭하게 동작했지만,
**매 실험마다 새 .cpp 파일을 만드는 패턴 자체가 이미 "새 지역 추가 시 도구 복제" 실패 신호를
스스로 재현하고 있습니다.** 다음 단계로 넘어가기 전에 이 세 도구의 로직(크롭→축소→팔레트→
저장→프리뷰)을 **하나의 매개변수화된 도구 + `proto_one.manifest.json`과 같은 성격의 매니페스트
파일**로 합쳐야, 위 표의 "선행 조건 충족 시" 칸이 실제로 달성됩니다.

## 7. 유지보수 난이도 표 (선행 조건 완료 가정)

| 작업 | 난이도 | 이유 |
|---|---|---|

| 암반 표시 크기 변경 | 재생성 도구 실행 필요 | 크롭 비율은 데이터, 재생성은 필요(코드 아님) |

| 타일 크기 변경 | 코드 수정 불필요, 재생성 도구 실행 필요 | tileSize는 이미 JSON에서 읽음(decision 0009) |
| 기존 결과 복구 | **구조상 위험(매니페스트 부재)** | prose 보고서만 있고 기계가 읽을 이력 파일이 없음 |
| 반복 프리뷰/게임 캡처 재생성 | 설정 또는 에셋 교체만 | 이미 잘 동작(세 도구 전부 이 패턴 보유) |

## 8. 실패 신호 점검

| 신호 | 현재 상태 | 심각도 | 회피 방법 |
|---|---|---|---|
| 역할별 하드코딩 증가 | 아직 없음(9개 역할은 role-agnostic 코드 공유) | 낮음(주의는 필요) | `inner` 처리를 `if(role==0)` 인라인이 아니라 `Tileset`에 `samplingMode` 필드로 선언 |
| 특정 이미지 크기 종속 | **이미 존재** — `TerrainTiles.cpp:163`가 아틀라스=`max(variants)*tileSize` 강제 | 중간 | 이 assert를 9-role 아틀라스 전용으로 좁히고, `inner` 매크로는 별도 검증 |
| 수작업 UV 숫자 증가 | 아직 없음. 제안 구조가 이를 원천 차단(하드웨어 반복) | 낮음 | 구현 시 "매크로 크기를 코드에 상수로 박지 말 것"을 조건으로 명시(10절) |
| 아틀라스/설정 중복 관리 | 낮음(JSON이 단일 소스) | 낮음 | 유지 |
| 조립기·런타임 규칙 불일치 | 아직 조립기 없음 — 향후 위험 | 중간(모서리/slab 작업 시) | 조립기 출력을 실제 `Terrain::pieces()` 지오메트리로 검증하는 테스트 추가 |
| 원본-최종 에셋 관계 추적 어려움 | **이미 관찰됨** — 이번 세션에서 "E1을 만든 정확한 크롭 좌표"를 prose 보고서에서 재확인해야 했음 | 중간 | `proto_one.manifest.json`처럼 raw 경로+크롭+팔레트 파라미터를 기록하는 매니페스트 |
| 테스트가 Avatar Lake 데이터에 종속 | **이미 존재** — `TerrainTilesTests.cpp:46`이 실제 `avatar_lake.json`과 실제 아틀라스 PNG를 직접 로드 | 중간 | 새 지역 추가 시 대비해 합성 픽스처 tileset으로 일부 테스트를 옮기는 것을 검토(이번 단계 필수는 아님) |
| 새 지역 추가 시 도구 복제 필요 | **이미 존재**(6절) | 높음 | 세 도구를 매개변수화된 하나로 통합 |
| 컴포넌트 경계마다 수동 수정 | 없음, 제안 구조도 자동(컴포넌트 bounds 사용) | 낮음 | 구현 시 반드시 `component.bounds.position`을 원점으로 자동 사용 |
| 미술 수정이 렌더링 코드 변경으로 이어짐 | 지금까지는 아님(3개 도구 모두 오프라인, 렌더러 무수정) — 단, `inner`를 매크로로 전환하는 **최초 1회**는 렌더러 변경이 불가피 | 낮음(1회성) | 1회 변경 이후에는 art 반복이 다시 도구/데이터만으로 가능하도록 설계(10절 조건) |

## 9. 다른 역할용 raw 생성 전에 확정할 계약

| 항목 | 결론 |
|---|---|
| 역할별 필요한 raw 종류 | `top`(암+풀), `side`(암 절단면, 좌우 겸용 반전 가능), 필요시 `bottom` 전용(그늘 톤이 side와 다를 수 있음 — 아트 검토 필요) |
| 크기/방향 | 원본은 지금처럼 정사각형 고해상도 유지, 최종 크롭 비율(스케일)은 매니페스트 값으로 관리 |
| 투명도 | 암반 본체는 불투명 유지(완전 불투명 RGB 정책 유지). 모서리/`slab` 조립 시에만 알파 마스크 필요할 수 있음 |
| 공통 팔레트 규칙 | **전 역할이 같은 소스에서 추출한 팔레트를 공유**해야 함(색 단절 방지) — inner의 14색 팔레트를 기준으로 확장 |
| 암반/풀·그늘 분리 | 유지(`top`만 풀, 나머지는 순수 암반) |
| 반복 가능 방향 | inner=양축, top/bottom=가로, left/right=세로, 모서리/slab=없음(3절 표) |
| 반복 주기 | 매니페스트의 크롭 비율 값(E1=75%가 현재 후보) |
| 경계가 맞아야 하는 위치 | 매크로 역할은 자기 반복 경계, 모서리/slab은 조립 이음매(조립기 존재 후 결정) |
| 파생 가능한 역할 | `left`/`right`는 `side` 1장의 반전, `top_left`/`top_right`는 모서리 1장의 반전, `bottom_left`/`bottom_right`도 마찬가지 가능성 — 최종은 아트 리뷰 |
| 모서리/`slab` 조립 방식 | 아직 없음 — 별도 조립기 도구 필요(이번 단계 범위 아님) |
| 매크로-경계 좌표 관계 | "1 world unit ≈ 1px" 가정이 실제 카메라 줌과 맞는지 아직 미검증(이전 raw_import_report.md에서도 지적된 열린 질문) — `top`/`side` 작업 전에 `Display.cpp`/`Camera.cpp` 값으로 확인 필요 |

**raw 원본 개수 결론(재확인)**: 10개 역할 각각에 원본이 필요한 게 아니라, 반전/조합을 활용하면
최소 2장(`top`+`side`)에서 최대 5장(`bottom` 전용, 모서리 전용 추가 시) 사이입니다. 정확한
숫자는 아트 리뷰 대상이며 이번 보고서가 결정하지 않습니다.

## 10. pane0 / Codex CLI 전달용 지침

> 아래 절은 그대로 복사해 전달할 수 있도록 구현 코드 없이 원칙만 담았습니다.

### 반드시 유지해야 할 설계 원칙

1. **역할 판정(충돌 기반, decision 0009)은 절대 건드리지 않는다.** `Terrain::components()`,
   `Terrain::pieces()`의 role 판정 로직(top/bottom/left/right/corner/slab 분류)은 그대로 둔다.
2. **9개 비-`inner` 역할의 아틀라스-변형 시스템은 그대로 유지한다.** `tileHash(cell,seed)%variants[role]`은
   `inner`를 제외한 나머지에 계속 쓴다.
3. **`inner`만 컴포넌트 로컬 연속 UV + `sf::Texture::setRepeated(true)`로 전환한다.** UV 원점은
   항상 `component.bounds.position`이어야 한다(월드 절대 좌표 금지 — decision 0009의 "공통 격자"
   계약과 어긋남).
4. **매크로 텍스처의 어떤 변형을 쓸지는 셀 단위가 아니라 컴포넌트 단위로 해시한다.** (사용자가
   이미 요구한 "한 덩어리 안에서는 한 텍스처만" 원칙을 만족시키는 유일한 방법.)
5. **tileSize, 매크로 텍스처 크기, 변형 목록은 전부 JSON/매니페스트 데이터다.** 코드에 어떤 숫자도
   상수로 박지 않는다(decision 0009가 이미 이 원칙을 선언했다 — 그대로 계승).

### 변경해도 되는 범위

- `Terrain::Tileset` 구조체에 `inner` 전용 필드 추가(예: 매크로 이미지 경로 목록).
- `TerrainTiles.cpp`의 아틀라스 치수 검증을 "9-role 아틀라스용"과 "`inner` 매크로용"으로 분리.
- `avatar_lake.json` 스키마 확장(기존 `roles`/`tileSize` 필드는 그대로 두고 새 필드만 추가 — 하위
  호환 유지).
- 세 개의 실험용 .cpp 도구(`normalize_avatar_lake_tiles.cpp`, `raw_import_experiment.cpp`,
  `raw_import_scale_experiment.cpp`)를 하나의 매개변수화된 재생성 도구로 통합.
- `proto_one.manifest.json`과 같은 성격의 매니페스트 파일을 `assets/tiles/avatar_lake/`에 신설.

### 변경하면 안 되는 범위

- `Terrain::components()`/`connected()`/`span()` — 충돌 기반 role 판정 로직 자체.
- 9개 비-`inner` 역할의 UV 계산 방식.
- `tileSize`를 JSON이 아닌 다른 곳(코드 상수, 커맨드라인 등)에서 읽게 만드는 것.
- `rock_inner_01.png`/`rock_inner_02.png`를 포함해 지금까지의 실험 결과물을 덮어쓰는 것 — 새
  파일로 추가하고 어떤 것을 채택했는지는 매니페스트에 기록한다.

### 수동 UV·역할별 하드코딩을 방지하는 조건

- 매크로 텍스처의 실제 픽셀 크기(예: 80×80)는 **이미지 파일 자체에서 읽어야 한다** — 코드에
  "80"을 상수로 박지 않는다.
- `inner` 분기는 `if(role==0)`처럼 역할 번호를 인라인 비교하지 않고, `Tileset`에 명시적인
  `samplingMode`(atlas | continuousMacro) 같은 필드로 선언한다 — 나중에 `top`/`side`가 같은
  방식을 쓰게 되어도 역할 번호 나열이 늘어나지 않도록.
- 크롭 비율, 팔레트 색상 수, 재생성 파라미터는 전부 매니페스트 JSON에 두고 도구는 그것만 읽는다.

### 데이터 또는 설정으로 노출해야 할 항목

- `inner` 매크로 이미지 경로(들) 및 변형 목록
- 원본(raw) 경로와 크롭 비율(현재 실험의 75%/50% 값)
- 팔레트 색상 수와 추출 파라미터
- (향후) `top`/`bottom`/`left`/`right`가 매크로 방식을 쓸지 여부

### 필요한 테스트와 실제 게임 캡처

- `TerrainTilesTests.cpp`에 `inner` 컴포넌트 로컬 연속 샘플링에 대한 지오메트리 테스트 추가
  (음수 좌표 컴포넌트, 서로 다른 컴포넌트 간 위상 독립성 등).
- 실제 `preview`/`run_avatar_lake.bat` 실행 결과 스크린샷(현재 회색 도형이 아닌 실제 텍스처가
  덮인 지형)을 캡처해 확인 — 오프라인 mockup이 아니라 실제 렌더 경로로 최소 1회 검증.
- 기존 아틀라스(9-role) 관련 테스트는 그대로 통과해야 함(회귀 확인).

### 기존 방식으로 복구할 수 있는 조건

- 매니페스트가 이전 raw 경로/크롭 값을 기록하고 있어야 "되돌려라"가 가능하다 — 매니페스트 신설이
  선행되지 않으면 복구는 사람이 prose 보고서를 다시 읽는 수작업이 된다(현재 상태).

### 구현 완료 전에 사용자 확인이 필요한 지점

1. `inner` 매크로로 **어떤 파일**(E1_medium 그대로인지, 재조정본인지)을 채택할지.
2. `top`/`bottom`/`left`/`right`도 매크로 방식을 쓸지, 기존 20×20 아틀라스 타일로 남길지(9절의
   열린 질문 — 이번 보고서는 결정하지 않음).
3. "1 world unit ≈ 1px" 가정을 실제 카메라 줌 값으로 검증한 뒤 진행할지.
4. 모서리/`slab` 조립기를 만들지, 아니면 당분간 손으로 그린 전용 아트로 대체할지.
